Ideation: Guarding the plugin against MCP tool-name drift

Date: 2026-10-08 Topic: mcp-tool-name-drift-guards Mode: repo-grounded Role: Technology Architecture of Enterprise Architecture

Focus: this plugin relies on two different MCP servers, which are continuing to evolve and include some schema changes in terms of tool names. Consider how we might guard against tool name changes breaking the plugin or degrading performance more proactively.

Codebase Context

  • Two servers, two naming schemes. .mcp.json bundles one server today, GlassFrog Extended (key glassfrog-extended, IP-owned, 101 snake_case tools such as glassfrog_get_role). GlassFrog's official MCP (app.glassfrog.com/api/v5/mcp, 36 camelCase tools such as glassfrog_getRole) arrives as a claude.ai or Cowork connector. #340 plans to bundle it as the default.
  • The citation surface is large and hand-typed. Shipped markdown cites 51 distinct bare tool names about 300 times. There is no alias layer or capability indirection. #337 found seven of those names on neither server, with 69 citations between them. They are v3-era names that outlived the v5 cutover, and a one-off grep during planning found them, not a guard.
  • The prefix is not stable. Observed prefixes: mcp__plugin_holacracy_glassfrog-extended__, mcp__glassfrog-extended__ (user scope), mcp__GlassFrog_Extended__ and mcp__GlassFrog_Official__ (Cowork), and UUID-named claude.ai connectors. Claude Code dedupes plugin and connector servers by endpoint URL, so a user-scope server with the same URL silently changes the prefix. agents/holacracy-coach.md hard-codes one prefix in 107 names (#338).
  • The eval tier cannot see a rename today. evals/stub/glassfrog_stub.py:57-71 hard-codes 7 read and 4 write tools, so a name the stub does not advertise is simply absent. The preflight at run-behavioural-eval.py:641-646 only fails on an empty tool list. made_a_call (:927-935) counts any tool_use, including a call to a dead name. EVENTS_WORTH_KEEPING drops tool results, and the stub's tool dicts are not in the skip-cache key.
  • Building blocks already exist. --validate-only reads a session's tool list with no model turn and no API cost. Three alarms share a 0/1/2 exit contract, tracking issues that close themselves, and "exit 2 on no evidence". skills-lint.sh has seven mutation-checked checks; CLAUDE.md still says six. glassfrog-mcp-server/src/tools/__tests__/registered-tools.test.ts already keeps an EXPECTED_TOOLS array of Extended's registered names. The session-start hook's conditional directive (#335) already matches tools by name suffix from any server.
  • Past learnings. Check the live MCP surface before trusting in-repo reference docs (docs/solutions/tooling-decisions/glassfrog-v5-inherited-context-single-call.md). A tool that reports success while silently doing less is the expensive failure: "A tool that fails loudly costs one minute; this one costs the full latency of the work you thought you dispatched." (create-trigger-mcp-builds-a-weaker-routine-than-the-ui.md).
  • External context. MCP has no ratified tool versioning. The convention is that tool names are stable identifiers, and SEP-2596 proposes an Active→Deprecated→Removed lifecycle. Prior art: mcp-pact (consumer-driven contracts for MCP), ToolDiff and mcpdiff (classify surface changes), and ai-tool-guard (a fingerprint per tool schema).

Boundary

#337 (dead names), #338 (coach prefix) and #340 (official server as default, plan being written in another session) are existing work. The ideas below build on them or stop them recurring, and they stay out of #340's routing design.

Topic Axes

  • Citation surface: how shipped markdown names tools (bare or fully qualified names, dead names, argument names).
  • Upstream change detection: knowing what each server exposes, and noticing when it changes before users do.
  • Runtime resolution: which server and prefix a session has, and how a capability binds to whatever tool exists.
  • Degradation measurement: detecting silent quality loss when a tool is missing or renamed.
  • Ownership and feedback loop: IP owns Extended and GlassFrog owns Official. Who hears about breakage, and how fixes flow both ways.

Ranked Ideas

  1. Tool-surface lockfile with generated consumers
  2. Make dead-tool calls loud in the eval tier
  3. A fourth alarm: scheduled drift check with blast radius
  4. A consumer contract the Extended server's CI must satisfy
  5. Cite capabilities, not tool names
  6. /holacracy:doctor: an in-session binding report
  7. A minimum equipment list per skill

I1. Tool-surface lockfile with generated consumers

Description
Commit one snapshot per server, contracts/<server>.tools.json. It holds tool names, argument schemas and a read/write class, reduced to types like glassfrog-schema-capture.py output so no real data enters the public repo. Extended's snapshot can come from the server repo's EXPECTED_TOOLS and source without OAuth. Official's comes from an operator-run authenticated tools/list. Four lists that are hand-maintained today are then generated from it: #337's known-names lint set, the stub's READ_TOOLS/WRITE_TOOLS (the deliberate defect overlay stays hand-written), the coach's allow and deny lists, and the preflight's expected-tools assertion. The snapshot hash joins the eval skip-cache key.
Basis
direct: the stub's hand-written dicts (evals/stub/glassfrog_stub.py:57-71). The stub is outside the skip-cache key inputs. #337's acceptance asks for a check against "the eval stub's tool list or a committed snapshot", so the snapshot has no home yet. The coach's deny list has already drifted: it names 48 write tools but not Extended's newer glassfrog_set_project_tags/glassfrog_set_action_tags. external: lockfiles; ai-tool-guard's per-schema fingerprint.
Rationale
Four lists already drift on their own, and one has drifted. With one source, a rename is one reviewed diff, and the snapshot's git history becomes the dependency's changelog. Ideas I2, I3 and I4 all read from it, so it comes first.
Downsides
Generated files in a repo whose product is hand-written markdown. Official's snapshot stays operator-local, so it can go stale; I3's freshness gate addresses that. Overlaps #337's "committed snapshot" option; what is new here is the generated consumers.

I2. Make dead-tool calls loud in the eval tier

Description
Four changes to run-behavioural-eval.py and its suite. (a) Every graded leg first runs the zero-cost --validate-only preflight and asserts the expected tools are in the session's tool list. (b) A tool_use naming a tool missing from that list becomes a sixth execution-failure condition. (c) tool_result errors are kept in events.jsonl. (d) A per-PR drift drill in run-behavioural-eval.test.sh renames one stub tool, replays a plan through the fake executor, and asserts the run fails. The drill would fail today, and that failure is the point.
Basis
direct: made_a_call = any(block.get("type") == "tool_use" …) at run-behavioural-eval.py:927-935 counts dead-name calls as calls. The preflight's only tool check is if not tools: return False, "stub advertised no tools" (:641-646). EVENTS_WORTH_KEEPING = ("system", "assistant", "result") drops tool results. The tension-triage no_writes floor is non-discriminating, so a write that could not be built passes the same as a refusal. CLAUDE.md: "A run that did not really happen must fail every assertion, not pass the negative ones."
Rationale
This is the one verified place where the repo's own instrument reports green while a cited tool does not exist. It has the same shape as #226: a healthy transcript that measured nothing. It is free and offline, and it extends a pattern the runner already has rather than adding a new one.
Downsides
It changes what a green nightly run means, and past baselines may flip. The stub's response to an unknown tool name should be confirmed before relying on (b).

I3. A fourth alarm: scheduled drift check with blast radius

Description
scripts/tool-surface-drift-check.sh diffs each server's live surface against the I1 lockfile on a schedule. It follows the existing alarm contract: exit 0/1/2, a tracking issue that closes on recovery, --dry-run, and exit 2 when the surface could not be read. Each finding is joined to a citation index, for example "glassfrog_list_metrics removed; 15 citations in 3 files". A second section lists unclaimed tools: tools a server gained that no skill cites, so a skill still doing an 18-call traversal learns a single-call tool exists. Extended runs in CI from its source on GitHub. Official runs operator-local with a token, like the first two alarms. A freshness gate blocks a release when the Official snapshot is older than N days. A schema-fingerprint step that guesses "rename vs removal" is optional, because real renames usually change arguments too.
Basis
direct: schema capture is "a one-time manual process", and the Extended changelog is read by hand (upstream-detection dossier). #337 was found by a one-off grep. CLAUDE.md: "2 includes 'nothing to measure.'" The v5 learning records a constraints doc that missed glassfrog_get_role_context and glassfrog_list_role_policies. external: ToolDiff and mcpdiff classify changes as breaking, additive or neutral.
Rationale
The plugin learns about a rename the day it ships, with the affected files already listed, before any user hits it. It is detection in both directions: names that broke, and capability the plugin is not using.
Downsides
A fourth scheduled job with its own noise budget. The Official leg needs someone to own the credential, and it sees nothing on the days nobody runs it. A field readout from real session transcripts (rejected as a separate idea) would fit here as a later section.

I4. A consumer contract the Extended server's CI must satisfy

Description
The plugin's lint derives consumed-tools.json from its own citations: each tool and argument it depends on, generated, never hand-written. glassfrog-mcp-server's CI fetches it from the plugin's stable branch, and its existing registered-tools.test.ts fails a PR that removes or renames a consumed tool without a deprecation window. During that window the old name stays as an alias described "DEPRECATED, use X". For the Official server, which IP does not control, the same file is the concrete artifact to attach when reporting a break to GlassFrog. Today that path is glassfrog-mcp-server#219, "Report to GlassFrog", with no defined channel.
Basis
external: mcp-pact, where agents declare the tools and arguments they depend on and CI verifies the server still provides them; Pact consumer-driven contracts; SEP-2596 deprecation lifecycle. direct: the owner dossier records "no formal coordination/deprecation policy with either server", and the v5 cutover "replaces v3 client wholesale", which is how #337's names were orphaned. The verifier confirmed EXPECTED_TOOLS exists in the server repo, which gives the contract somewhere to plug in.
Rationale
Every other idea catches drift after it ships. This one stops the drift IP causes itself, on the server with three times the tools, at the PR where the rename is written. That is the cheapest point to catch it.
Downsides
It couples two repos' release processes; the server's CI would block on the plugin's state. No leverage over Official beyond a clearer request.

I5. Cite capabilities, not tool names

Description
Skills cite a stable capability such as role.get or tension.create. One table maps each capability to its tool name and argument differences on each server: snake_case on Extended, camelCase on Official, and createTension's label/meeting_type. A new lint check fails any raw glassfrog_* name outside the table. There are two shapes. A markdown table in skills/shared/, cited by anchor, reuses check 2's citation machinery and keeps the product as markdown. A build step that renders names into shipped files is more robust but adds a build. This should go into #340's plan as an input rather than be planned separately: it gives #340's routing a home without deciding the routing.
Basis
direct: "51 distinct bare snake_case tool names, ~300 citations … no alias layer or capability indirection" (citation dossier). glassfrog_get_circle alone has 20 references. STRATEGY.md describes the connector as a seam so the backend can be repointed without touching skills, an intent ADR-0005 records that is not implemented. external: feature detection rather than user-agent sniffing.
Rationale
Supporting two servers with different naming conventions roughly doubles the citation surface unless the names live in one place. This decides whether #340 lands as about 300 edits or 51 table rows, and every later rename after that.
Downsides
One more hop for a reader of a skill. The model may follow an indirect citation less reliably than an inline name, which needs eval evidence. High effort, and it collides with an in-flight plan.

I6. /holacracy:doctor: an in-session binding report

Description
A command, also usable as an optional step in actor-and-role-resolution.md, that lists the session's glassfrog_* tools by name suffix and groups them by prefix form (plugin, user scope, Cowork, UUID connector). It compares them with the I1 lockfile or the I5 table. It reports which cited tools are missing, where two servers overlap, and where a user-scope server with the same URL is shadowing the plugin's. The output is a block the user can paste into an issue.
Basis
direct: ADR-0008 A6 records the manual work needed on 2026-10-08 to find claude.ai connectors answering calls under UUID names, unseen by the local store. #332: connectors never appear in the local OAuth store. hooks-handlers/session-start.sh around line 482 already matches "a tool whose name ends in glassfrog_get_me … from any server". external: Claude Code dedupes servers by endpoint URL.
Rationale
It is the only detector here that reaches Cowork and claude.ai sessions, which CI and the operator-local alarms cannot read. "The plugin seems off" becomes one command, and the report to a server owner comes with evidence attached.
Downsides
It is pull, not push: it helps only when someone runs it. A model-run comparison is less exact than a script.

I7. A minimum equipment list per skill

Description
This borrows from aviation's minimum equipment list. Each skill and command declares, in frontmatter, the capabilities it needs and how it behaves without each one. requires-capabilities marks a no-go capability: stop and tell the user. enhanced-by marks a go-if capability with a named, reviewed fallback, such as "work from the dispatcher payload and label the output payload-only". Lint check 3 validates the declarations against the lockfile. A shared procedure forbids any write through a guessed substitute name. An eval assertion checks that, under a stub missing a required capability, the transcript names the gap. The declarations can also generate I4's contract, so one statement feeds the build, CI, the cross-repo check and I6.
Basis
direct: agents/holacracy-coach.md:40-43, "If GlassFrog is not connected, say so and work from the payload the dispatcher gave you", is an ad-hoc fallback entry for one agent. The no_writes floor cannot tell a failed write from a refusal. The create-trigger learning: silent degradation costs "the full latency of the work you thought you dispatched." external: FAA MMEL/MEL dispatch practice.
Rationale
When a tool disappears, the costly failure is a plausible substitute producing a weaker result that looks normal, not the error. This makes the fallback a reviewed design choice and makes "degraded" visible in the output. It answers what a missing tool should do, which neither #337, #338 nor #340 addresses.
Downsides
Touches every skill's frontmatter. It overlaps #340's routing and I5, so it fits best as a follow-on once those settle.

Grounding Context

Codebase context. scripts/run-behavioural-eval.py drives the Claude Code CLI headlessly. For each eval case it runs two configurations — with_skill via --plugin-dir, and a without_skill control — with N repeats each (nightly N=3). Every execution is a fresh subprocess.run() with an empty CLAUDE_CONFIG_DIR, a sandbox cwd outside the checkout, --strict-mcp-config, and a generated stub-MCP config pointing at evals/stub/glassfrog_stub.py. A second, separate model subprocess then grades the transcript against per-case assertions. .github/workflows/skills-eval.yml runs the whole thing nightly and on workflow_dispatch; per-PR CI runs only the offline suites, which make no API calls at all.

That shape produces roughly 24 executions plus 24 grading passes per nightly run, at about two minutes per execution against a 90-minute job ceiling. No session is ever resumed or reused, so nothing in the harness gets any API-side prompt-cache benefit today. The evals/benchmark.json baseline is committed unmeasured, with null token figures.

The finding that reorganised this ideation. Three grounding scouts disagreed about what the harness records. Reading the code settled it, and the answer is worse than any of the three guessed: usage_tokens() sums input_tokens, output_tokens, cache_creation_input_tokens and cache_read_input_tokens into a single integer before anything is stored. Cache hit rate is therefore not merely unreported — it is unrecoverable from the artifacts. Enabling prompt caching today would produce no observable change in anything the harness writes.

Past learnings. Nothing in docs/solutions/ addresses caching for eval harnesses. Two adjacent lessons transfer: ADR-0012's cost-stratified tier model (the cheap tier makes no model calls, so caching has no value there), and a tooling-decisions entry recording that the in-repo API constraints doc had gone stale — probe the live surface before designing against documentation.

External context. Anthropic prompt caching allows up to four cache_control breakpoints; reads cost roughly 0.1× base input, writes 1.25× at the five-minute TTL or 2.0× at the one-hour TTL, which only pays off past about five to seven reads. Matching is exact-prefix — any change before a breakpoint invalidates everything after it. Independent write-ups converge on the Claude Code CLI being fragile here: a per-invocation dynamic header, plus three documented defects that break the prefix on resumed turns, measured at roughly a 66% hit rate before patching. The Message Batches API offers a flat 50% discount for non-interactive work and stacks with caching discounts. Inspect AI ships a cache-prompt option and batch mode as explicit scale knobs, and its cost doctrine — deterministic scorers wherever possible, model-graded scorers reserved for genuinely open-ended judgment — matches this repo's own stated principle almost exactly.

Topic Axes

  • Executor session construction — how each arm's CLI session is spawned, isolated, pinned, and never reused; whether cache breakpoints are reachable through this invocation path at all.
  • Grading pass — the separate scoring call: prompt shape, the identical-across-calls preamble and schema, transcript payload, batchability, grader model choice.
  • Run economics — what executes and how often: cases × configs × repeats, scheduling, result caching, early stopping, tier placement.
  • Cost observability — measuring and reporting token, cache and USD cost per run, per case, per arm; regression alarms on cost, not only on pass rate.
  • Assertion layer — free deterministic Python checks versus model-graded assertions; how much graded surface could move to free checks without losing discriminating power.

Ranked Ideas

  1. Unbundle the token ledger — make cost measurable at all
  2. Settle whether the cache prefix is stable, before writing any caching code
  3. Rebuild grading as a batched, cached, blinded scoring stage
  4. Skip what has not changed — one decision at three possible scopes
  5. Log reads in the stub, then measure whether assertions discriminate
  6. Spend repeats where the signal is ambiguous
  7. Own the request body — the fork the harness never explicitly took
1. Cost observability Confidence 95% Complexity Low-Medium

Unbundle the token ledger — make cost measurable at all

Description
Record five distinct fields per arm — input, output, cache creation, cache read, and total_cost_usd — instead of one collapsed integer. Capture the grader's usage as well as the executor's. Render cost deltas in scripts/eval-report.py alongside pass rate, seed benchmark.json's null tokens block honestly, and add a cost-regression alarm built on the chassis the repo already uses three times over: 0/1/2 exit codes, --dry-run, fixture injection for offline CI, tracking-issue upsert. Optionally report cost against a denominator — tokens per discriminating assertion resolved — so interventions can be ranked rather than merely totalled.
Basis
direct: run-behavioural-eval.py:551-560 sums all four usage fields into one int and returns it; :877 stores that single value in timing.json from outcome["events"] — the executor's stream only. The metrics dict at :541-547 carries no token field at all. grep total_tokens scripts/eval-report.py returns nothing. benchmark.json's tokens block is null across mean, stddev, min and max. The grader's own result payload is parsed at :782, so its usage is available and simply never read.
Rationale
Every other idea in this document is unfalsifiable until this lands. You cannot show that batching saved 50%, that a cache breakpoint raised hit rate, or that a skip-if-unchanged cache paid for itself, when roughly half the nightly spend is structurally invisible and the numerator and denominator of the cache ratio were added together before storage. The repo already articulated this exact standard one layer over: a benchmark that cannot name its model makes a model upgrade indistinguishable from a skill regression. A benchmark that cannot name its cache-hit rate makes a caching win indistinguishable from noise. And because the baseline is still unmeasured, the fields can be defined correctly before it is seeded rather than re-seeded afterward.
Downsides
Widens the artifact schema before any of it is validated against a real graded run, so the first seeding may still need revision. The cost-per-discriminating-assertion denominator is a genuinely debatable metric choice and should not block the plain unbundling. Adding a fourth alarm adds maintenance surface to a repo that already carries three.
2. Executor session construction Confidence 85% Complexity Low

Settle whether the cache prefix is stable, before writing any caching code

Description
Before wiring a single cache_control breakpoint, determine empirically whether the Claude Code CLI's per-invocation dynamic header sits before or after where a breakpoint would go — that is, whether prefix caching is reachable at all through a headless spawn. Reuse the harness's own --validate-only pattern, which starts a real session, reads what it needs, and kills it before any model turn. If a request-capture affordance turns out to exist and works offline, the stronger version of this move is to keep a byte-differ over two identical invocations as a permanent free gate — the reproducible-builds approach of pairing nondeterminism neutralisation with a regression test on byte-identity.
Basis
direct: probe_session()'s docstring records that the CLI emits its system/init event before it authenticates, which is exactly why --validate-only costs nothing. external: two independent write-ups converge on the CLI emitting a unique per-invocation header that guarantees a cache miss without session reuse, and on three further defects that break the prefix even on resumed turns.
Rationale
This is the gating question for everything else on the executor axis, and it is the cheapest item in this document. A warm-up call to pre-pay a one-hour-TTL write, a resumed-repeats scheme, or any breakpoint placement is undecidable until it is answered — and each of those is far more expensive to build and unwind than the probe is to run. The repo has already recorded the general form of this lesson in docs/solutions/: probe the live surface rather than designing against documentation that may have gone stale.
Downsides
The answer may be "no, not reachable through this path" — which redirects effort to idea 7 and its unresolved conflict with the repo's testing philosophy. The byte-differ half rests on a request-capture capability that has zero footprint in this repo and was not substantiated during verification; if capturing a request needs a live round-trip, it cannot be the free per-PR gate described and would violate the rule that per-PR CI makes no API calls.
3. Grading pass Confidence 80% Complexity High

Rebuild grading as a batched, cached, blinded scoring stage

Description
The grader is a stateless, tool-free, schema-constrained call — a Messages API call wearing a CLI costume. Move it off the interactive CLI and restructure it three ways at once. Put the fixed preamble and JSON schema behind a cache_control breakpoint and the per-case payload after it. Submit all grading as one Message Batches job after the executor matrix completes, rather than interleaving a grading round-trip between every pair of executions. And grade both arms of a case inside a single call with the transcripts shuffled and labelled A/B, un-blinded in Python afterward — which halves the fixed portion and turns two absolute judgments into the one paired comparison the benchmark actually reports. Carry one property through the rewrite: a grading call that did not happen must be reported as unsettled and retried, never scored.
Basis
direct: the grader command at :759-766 is claude -p … --output-format json --json-schema … --tools "" — no tools, no plugin, no agentic loop. GRADER_PROMPT's preamble and contract at :711-726 plus GRADER_SCHEMA are byte-identical across every call; only {writes} and {transcript} vary, and assertions and ground truth come from the shared case dict. The call site at :859 sits inside the per-run loop, which is what interleaves it. external: the Batches API's 50% discount stacks with cache-read pricing; Inspect AI ships batch mode as an explicit scale knob; Dorfman pooled testing and clinical-trial blinding supply the paired-judgment structure.
Rationale
This is where the cheap, uncontroversial money is: none of it touches hermeticity, the stub, the fixtures, or a single assertion's content. It is also the one place where the cost move and a methodological improvement are the same move — a paired within-call comparison removes between-call judge drift, which is a free reduction in exactly the variance the repo says makes a nightly job ignorable. Four of the five ideation agents reached this independently from separate contexts.
Downsides
The real cost is architectural, and verification flagged it: the Batches API is asynchronous with an up-to-24-hour ceiling, while the workflow derives its entire budget from a single synchronous 90-minute job. Adopting it means restructuring into a dispatch-then-poll shape that no other idea here accounts for. Blinding is mandatory rather than optional — an unblinded grader seeing both arms can infer which came from the plugin and grade generously — and pooling repeats into one call carries the same correlated-judgment risk, so it needs the same discipline. Splitting a single call into a submit/reconcile pair also adds a failure mode the current synchronous design does not have.
4. Run economics Confidence 75% Complexity Medium-High

Skip what has not changed — one decision at three possible scopes

Description
Treat an eval case the way a build system treats an action: key its result on a hash of everything that could move it — case file content, skill content and version, fixture hash, model id, stub hash, CLI version — and skip re-execution when the key already has a fresh measured result. Three scopes are available and the choice between them is the decision, not three separate proposals. Narrowest: amortise only the without_skill control, which is a property of the base model and cannot change when this repo changes. Middle: a general per-leg action cache. Widest: retire the unconditional nightly clock entirely, running the full matrix on content change and a small canary periodically to catch base-model drift. Whichever scope is chosen, keep the free --validate-only session-shape probe running every night on both arms, so a replayed control still proves it registered no holacracy: command.
Basis
direct: skills-lint.sh's check 4 — a skill whose content changed also moved its version — already computes half the proposed cache key today. session_shape_error() at :278-280 rejects a control that leaked the plugin, and the free probe is what preserves that guarantee under replay. external: Bazel's action cache maps an input hash to a content-addressed result shared across CI runs.
Rationale
On a quiet night the nightly job re-executes and re-grades every case to produce a result identical to the one already committed — real spend against zero new information. Making cost scale with changes rather than with the calendar frees the 90-minute ceiling for the higher tiers the repo has deferred, without raising spend. The scope question matters because the widest version is the one that changes what "nightly" means to the team.
Downsides
Cache-key correctness is the whole risk: omit an input that actually moves results and the harness silently reports a stale verdict as current — a failure mode strictly worse than overspending. The control-only variant's headline arithmetic was asserted rather than derived during verification. The widest variant rests on a first-principles argument rather than repo evidence: skills, fixtures and CLI version can all change silently between nights, so "only the model varies" is not established. And any replay scheme interacts badly with a resumed-repeats design, which is one reason that idea was cut.
5. Assertion layer Confidence 90% Complexity Medium

Log reads in the stub, then measure whether assertions discriminate

Description
The stub records writes and nothing else, so every claim about what the assistant consulted — did it read the role's accountabilities before proposing, did it check sub-role tensions, did it invent a role it never fetched — has to be judged by a model reading a transcript. Log every call including reads, with sequence numbers, and extend the mechanical check vocabulary with read-presence and read-ordering kinds. That converts a large slice of currently-judged surface into free, deterministic, drift-proof checks. Three follow-ons ride on the same log and should be scoped separately rather than bundled: an assertion-level ledger recording whether each discriminating: true declaration has ever actually discriminated between arms; a repeatability study grading frozen transcripts N times to find assertions that flip on byte-identical input; and a graduation pipeline that demotes stable judged assertions to mechanical ones, gated on a mutation-verified replacement rather than on looking stable.
Basis
direct: evals/stub/glassfrog_stub.py:57-71 defines seven read tools against four write tools, but record_write() at :74-80 fires only on writes. The runner's own comment at :83-94 states the principle already: ordering claims are only checkable against a log, and checking them deterministically means they cost no tokens and cannot drift between nightly runs. external: gauge repeatability studies in measurement-systems analysis; metamorphic testing as used in compiler validation, which suggests a further free family of checks over generated fixture variants.
Rationale
This is the only idea here that raises discriminating power while cutting tokens, which makes it the one kind of cost reduction the stated constraint permits unconditionally. A grader can be talked into passing "it checked the accountabilities" by an assistant that merely says it did; a read log cannot. The repo already won this argument once for writes and stopped there because ordering was the only mechanically-checkable claim anyone noticed. It also closes a real gap in doctrine: the repo polices whether an assertion discriminates between arms and not at all whether it discriminates between identical inputs, which is a strictly worse defect and invisible in every artifact today.
Downsides
Expands the stub's contract and the case-file schema, and invites a re-audit of existing judged assertions — real work, and politically the first ledger will likely indict an assertion someone wrote and defended. The bundle spans very different sizes and risks and should be unbundled before anyone votes on it. The repeatability study is quietly defeated if grader-verdict memoisation is ever introduced without forcing misses for repeated grading of identical content.
6. Run economics Confidence 70% Complexity Medium

Spend repeats where the signal is ambiguous

Description
Every case currently gets a flat three repeats per arm whether or not its results are stable. Replace the fixed count with a sequential rule: run one repeat, and escalate only when the accumulated evidence is ambiguous — a case where the treated arm passes cleanly and the control fails cleanly needs no second observation, while a case whose first two repeats disagree deserves five. Same nightly budget, allocated by information rather than by uniform quota. One guard is load-bearing: a run that hit any of the five execution-failure conditions must not enrol as an observation at all, or the rule stops early on garbage.
Basis
external: Wald's sequential probability ratio test, developed for acceptance sampling where each observation is expensive and destructive, and its descendants in group-sequential clinical trial design; both typically terminate at around half the fixed-N sample size. direct: evals/README.md already treats a wide standard deviation as a defect in the case rather than a finding about the skill — but nothing in the harness acts on that.
Rationale
The harness is a paired experiment measuring a small treatment effect under high per-observation cost and high per-observation variance, which is precisely the regime where sequential designs dominate fixed-N. It also inverts the current failure mode: stable cases stop paying a 3× tax they do not need, and the budget moves to the cases where the answer is genuinely unclear. Discriminating power goes up, not down, for constant spend — and the repeat ceiling stops binding as the case count grows.
Downsides
Changes what the benchmark means statistically, so the baseline's variance figures are not comparable across the switch. Requires independent observations to be valid, which rules out combining it with any resumed-session repeats scheme and puts it in tension with replaying cached results as though they were fresh draws. Sequential designs are also easy to implement subtly wrong, and a wrong stopping rule produces confident nonsense rather than an obvious failure.
7. Executor session construction Confidence 45% Complexity High

Own the request body — the fork the harness never explicitly took

Description
The harness shells out to claude -p and therefore can never place a cache breakpoint: the prompt is one opaque string and everything expensive is assembled inside a binary it does not control. Rebuild the executor on the Agent SDK or the Messages API with an explicit tool loop, so the harness constructs the request, places its own breakpoints, and pins the prefix byte-for-byte across arms and repeats — retaining the CLI path as a second, periodic configuration that answers "does the real shipped product still behave this way".
Basis
direct: build_command() at :208-223 emits a flat argv — -p, --tools, --output-format, --strict-mcp-config, --mcp-config, --permission-mode, plus --plugin-dir and --model. No flag in that list can express a cache breakpoint.
Rationale
Whoever owns the request body sets the ceiling on every caching lever in this document. Today the answer is nobody in this repo, which is why cache_read_input_tokens is a number the harness observes rather than one it causes. It would also sidestep the CLI's per-invocation dynamic header entirely rather than working around it.
Downsides
This one is ranked last because verification found it in direct tension with the repo's own stated testing philosophy, and the idea as generated did not address that. The stub's docstring says the eval must exercise the actual command path precisely because a mock at the reasoning layer would test the prompt and miss what the plugin actually does wrong — and #226 exists because two different loading paths produced indistinguishable results. Demoting the CLI to occasional reintroduces the class of risk that fix was built to catch. It is also the largest rewrite proposed here, and idea 2 may show it is unnecessary.

Reading order

Ideas 1 and 2 are prerequisites rather than options: without the ledger, no result here is measurable, and without the probe, the executor-side ideas are undecidable. Idea 3 is the largest confirmed saving available and depends on neither. Ideas 4 and 6 cannot both be built as described alongside any resumed-session scheme, and idea 7 becomes relevant mainly if idea 2 returns a negative answer.
